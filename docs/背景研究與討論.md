# 背景研究與討論紀錄

這份文件記錄 Air Jam 查過的資料、分析過的數字、討論過的想法，以及試過但沒有用的做法，持續更新，每一節註明日期。設計規格在 [設計說明.md](設計說明.md)，做過的決定在 [決定紀錄.md](決定紀錄.md)。

## 1. 起點：Casio CT-FS1 與 Feel Sync（2026-11-25）

Casio 在 2026 年 11 月發表 CT-FS1 電子琴，主打 **Feel Sync** 技術：跟著歌彈，不會彈錯音。這是 Air Jam「不會樂器也能即興」的直接靈感。

### 1.1 產品資訊

- 61 鍵、觸鍵感應電子琴，機身和琴鍵同色（全黑或全白），連黑白鍵都不分，強調開了 Feel Sync 時按哪個鍵都不重要。
- 重量不到 10 磅（約 4.5 公斤），可以用變壓器或 AA 電池，內建立體聲喇叭，有耳機孔。
- 附 WU-BT10 藍牙 MIDI／音訊轉接器，和手機上的 Feel Sync App 連線。
- 價格：各來源說法不一。Hypebeast 寫 US$400，Notebookcheck 寫 US$399.99，MusicRadar 寫 $339／£335，德國售價 399 歐元。

### 1.2 Feel Sync 怎麼運作

1. 在 Feel Sync App 選一首歌。App 有內建曲庫，也可以匯入自己的 MP3／WAV；不支援串流服務。
2. App 分析歌曲的和弦進行、旋律與節奏。
3. 播歌時，演算法**即時修正玩家彈的音高**，讓它符合當下的和弦進行。說明書的說法是：彈的音會被修正成配合歌曲的和弦進行，單音和和弦都會修正。零售商描述為「即時重新對應（remap）鍵盤」。
4. 能處理轉調和複雜的過門（Engadget）。
5. App 有「延遲補償」設定，用來處理和弦修正跟不上歌曲的情況。

### 1.3 重要的理解：「和聲上正確」不等於「旋律上正確」

- 它保證的是**和聲上正確**：不會刺耳、不會走調。
- 它**不保證**彈出原曲那條旋律。機器不知道玩家「想」按哪個鍵，所以沒辦法把失誤改回原本該彈的音；它的做法是讓鍵盤上「不存在錯音」。
- 實際感覺是「跟著歌即興亂彈也好聽」：玩家負責節奏、力度和情緒，音高交給機器。
- **主旋律由原曲負責。**原曲音訊會一直播放（說明書有歌曲音量和鍵盤音量的平衡設定），玩家的角色比較像伴奏或合奏樂手。Casio 的介紹也說，感覺「就像自己在彈和聲」。
- 說明書**沒有**寫：按鍵的高低順序有沒有保留、音會對應到和弦內音還是調內音階。
- 「鍵盤負責和聲、玩家彈旋律」這種模式，說明書裡找不到（只有轉述 Engadget 的文章提到）。說明書只有：示範曲模式（Feel Sync 示範、標準示範）、App 播歌模式、Feel Sync 作用範圍（左半、右半或整個鍵盤，另一半照實際按的音發聲）。
- 有「中央聲道消除」功能（AUDIO IN Center Cancel）可以減弱人聲，但沒寫 Feel Sync 時能不能用。
- 限制：它不教音階、指法和鋼琴技巧（The Gadgeteer）。

### 1.4 對 Air Jam 的啟發

- 「和弦吸附」：把玩家的輸入吸附到目前和弦的音上，是 Air Jam 的核心（設計說明第 5 節）。
- 先分析整首歌、再播放，可以預告下一個和弦。
- 原曲照常播放，玩家負責伴奏或即興，不用負責主旋律。
- 和弦是程式猜的，要誠實告訴玩家。

## 2. 空中弦的靈感：手勢弦樂器影片（2026-11-25）

- 來源：一支 Facebook Reel（https://www.facebook.com/reel/1320325243578615 ，需要登入才能看；以下根據截圖描述）。
- 做法：用 MediaPipe 類的手部追蹤，雙手捏住拉出一條弦，放開後**弦停在空中**，可以存很多條，交錯成一整片。弦的**長度決定音高**，弦上有刻度（像尺規或琴格）。用手指撥弦，被撥的弦會彎曲、震動、發光（粉紅、青色等光暈）。
- 原作者的靈感來自 **Pat Metheny 的 42 弦「畢卡索吉他」（Pikasso guitar）**，一把有很多組弦、包含共鳴弦的吉他。
- Air Jam 自己加的部分：Feel Sync 式的和弦吸附、撥弦速度控制音量、撥弦位置控制音色、節奏判定與連擊、刷和弦、分析使用者自己的歌。
- **公開時要標註靈感來源**（影片作者、Pat Metheny、Casio Feel Sync）。

## 3. 早期設計想法的演變（2026-11-25）

1. **第一個想法**（還沒看到影片截圖前）：兩手捏出一條弦，弦的「高低」決定音高（吸附五聲音階），弦的「長短」決定音色或音量，像豎琴一樣上下掃過格子就發聲。
2. **看到截圖後改成**：弦留在空中、長度決定音高、用手指撥。比較像真的弦樂器，也能做出畢卡索吉他那種很多條弦的畫面。
3. **再加上 Feel Sync**：長度不直接換成頻率，而是換成「第幾格」，每格對應目前和弦的第 N 個和弦內音；換和弦時所有弦自動重新調音。
4. **定位改變**：一開始是當作教學範例構想的，後來決定先做成**給大家玩的完整遊戲**，之後再從完整專案拆出簡化版本當教學材料。

## 4. 電吉他音效能不能用合成做出來（2026-11-25）

可以做到「一聽就知道是電吉他」，大約是遊戲音效的等級，全部用 Web Audio 就能做：

| 效果 | Web Audio 做法 |
|---|---|
| 撥弦 | Karplus-Strong |
| Distortion／Overdrive | `WaveShaperNode` 削波 |
| 音箱模擬 | 低通（約 4–5 kHz）＋EQ，或 `ConvolverNode` 套音箱脈衝響應 |
| 娃娃音（Wah） | `BiquadFilterNode` 帶通，中心頻率約 400 Hz ↔ 2 kHz 移動 |
| Chorus／Flanger | LFO 調變的短延遲 |
| Delay | `DelayNode`＋回授 |
| Reverb | `ConvolverNode`＋程式生成的衰減雜訊 |
| 推弦／搖桿 | 改變播放速率 |

要點：
- **一定要有音箱模擬那一層。** 只有破音、沒有音箱模擬，聲音會又刺又沙。
- **破音時用強力和弦（根音＋五度）。** 三和弦加重破音會糊掉，所以破音音色下的和弦吸附要改。
- **用手控制娃娃音**：沒在撥弦的那隻手的高度取代腳踏板，這是 Air Jam 特有的玩法。
- 和專業音箱模擬軟體相比仍有差距，例如撥片觸弦聲、手掌悶音、回授嘯叫，要做得很真比較費工。

## 5. 吉他音樂類型與遊戲模式發想（2026-11-25）

| 類型 | 代表彈法 | 聲音 |
|---|---|---|
| 民謠／流行 | 刷和弦、分解和弦 | 木吉他 |
| 搖滾 | 強力和弦、破音刷奏 | 電吉他破音 |
| 金屬 | 悶音快速下撥 | 重破音 |
| 藍調 | 推弦、藍調音階即興 | 微破音 |
| 放克 | 切音、16 分音符 | 乾淨、短促 |
| 爵士 | 七和弦、九和弦，走旋律線 | 圓潤 |
| 古典／指彈 | 低音和旋律分開撥 | 尼龍弦 |
| 佛朗明哥 | 快速掃弦、拍琴身 | 激烈 |
| 雷鬼 | 只彈反拍短切音 | 輕快 |
| Bossa Nova | 拇指低音＋切分和弦 | 輕柔 |
| 烏克麗麗 | 刷奏 | 明亮 |
| 後搖滾／氛圍 | 長延遲、殘響 | 空靈 |

由這些類型整理出的遊戲模式：伴奏手、獨奏手、自彈自唱、指彈一人樂團、合奏、氛圍創作，另外還有曲風節奏模式和多種音色。細節寫在設計說明第 15 節。

**當時建議的優先順序：**
1. 伴奏手（第一版）
2. 音色切換（木吉他／電吉他＋手控娃娃音）
3. 獨奏模式（五聲音階＋推弦）
4. 自彈自唱
5. 曲風節奏、合奏、指彈

## 6. 命名（2026-11-25）

- 第一個名字是「空中弦」（air-strings）。因為之後要加其他樂器，改成以玩法命名：**Air Jam（`air-jam`，空中即興）**。
- 英文用 `air-jam` 而不是 `jam-air`：air 當形容詞放前面比較自然（就像 air guitar）。
- 空中弦保留為 Air Jam 的第一個樂器。之後可以加空中鼓、空中琴、空中特雷門琴、空中貝斯。
- **不要使用**「Pikasso／畢卡索」（Pat Metheny 吉他的名稱）和「Feel Sync」（Casio 的名稱）。
- 「Air Jam」這種常見組合可能已經有人用過；因為是非營利的遊戲，決定不處理撞名。

## 7. 搖滾範例歌的分析（2026-11-25）

擁有者提供兩首搖滾演奏曲（本機 `samples/sample 14.mp3`、`sample 21.mp3`，有版權、不提交；以下叫 s14、s21，各約 80 秒、48 kHz 立體聲）。**沒有人實際聽過分析結果是否正確**，以下都是訊號量測。

### 7.1 第一次分析（後來被推翻一部分）

方法：用 ffmpeg 轉成 44.1 kHz WAV，跑 Air Jam 當時的分析程式，再用 librosa 交叉比對。

| | s14 | s21 |
|---|---|---|
| Air Jam 舊版速度 | 107 BPM | 140 BPM |
| librosa `beat_track` | 107.7 | （當時沒有跑；之後量到 103.4） |
| 調性 | A 小調 | A（大調） |
| 和弦 | Am–G–F–E 一類 | 段落很亂：Fm、F#m、Gm、Am、D… |

當時的結論（**速度部分是錯的**，見 7.2）：兩首主奏都繞著 A 小調五聲音階；搖滾用強力和弦，所以大小調分不出來；主奏在中間聲道。

### 7.2 設計挑戰的重新量測與修正後的結果

Fable 重新量測（細節在 [搖滾獨奏_設計挑戰.md](搖滾獨奏_設計挑戰.md)），Opus 修正分析程式後用 `node tests/samples.test.mjs` 驗證：

| | s14 | s21 |
|---|---|---|
| 最小脈動 | 187.5 ms | 285.8 ms |
| 舊版的錯 | 一拍＝3 個脈動（107） | 一拍＝1.5 個脈動（140），每隔一拍落在兩個音中間 |
| **修正後速度** | **160 BPM**（一拍＝2 個脈動；80 也在脈動上，**待擁有者用耳朵確認**） | **104.9 BPM**（一拍＝2 個脈動） |
| 拍點落在脈動格線 ±40 ms 內 | 100% | 97.1% |
| 和弦段落邊界在小節線上 | 8/21 → 21/22 | 3/18 → 17/17 |
| 和弦 | Am–G…，F–G–Am–F–G–E–Am，30 秒後原樣重複 | 每 12 小節重複（像 12 小節藍調），但標籤仍亂 |

其他量測：
- **強力和弦：**三度音只有根音能量的約 15～30%；s21 上大三和弦和小三和弦模板的分數差只有 0.010。
- **s21 和弦標籤亂的原因：**貝斯整首在 A，節奏吉他是 A5–A6–A7 的 boogie 音型，加上鼓的雜訊；是和弦辨識的問題，不是拍子格線的問題。
- **主奏在中間：**s14 有一條 A4 以上的中間旋律約佔 23% 時間，91% 的音在 A 小調五聲音階；**s21 測不到主奏**，中間聲道 500 Hz～5 kHz 有 87% 是打擊樂，可能是伴奏帶。
- **兩首的節奏吉他都左右分開**（800 Hz～4 kHz 的 side／mid 能量比 0.59～0.70）。
- s21 中高音域的三度：C# 明顯多於 C（大調藍調）；s14 相反（C 多於 C#）。

### 7.3 試過但沒有用的做法

| 做法 | 結果 | 原因 |
|---|---|---|
| librosa `pyin` 追主奏音高 | 失敗：有聲機率中位數只有 0.01，音高卡在下限 | 混音太滿（破音吉他、鼓），單音追蹤器不適用 |
| 和聲顯著度（harmonic salience）追中間聲道主奏 | 有結果但不可靠：s21 追到的其實是節奏吉他的 riff | s21 沒有主奏；中位音高 A3 偏低，混到了 riff |
| 「兩套工具都說 107，所以對」 | 錯 | Air Jam 和 librosa 都偏好 110～120 BPM，不是獨立的證據 |
| 只追和弦根音（強力和弦模板）取代三和弦模板 | 只對一半：s14 反而更差（把 Am 判成 C5、多出 A#5） | s21 的混亂主要來自拍子格線錯誤，換對格線後三和弦模板就好很多 |
| 降低原曲中間聲道（讓玩家的 solo 取代原主奏） | 未實作，評估後不建議預設開啟 | s21 中間主要是小鼓，降下去只會削掉小鼓 |

### 7.4 分析用的工具與參數（第 7 節的可重現性）

分析腳本是暫存的，沒有保留；要重做時照以下設定（2026-11-25）：

- 轉檔：ffmpeg（2026-01 版）`ffmpeg -i <mp3> -ac 2 -ar 44100 <wav>`。
- Air Jam 分析：Node 25，直接呼叫 `src/core/analysis/analysis.js` 的 `analyzeSync`，左右聲道平均成單聲道。現在由 `tests/samples.test.mjs` 取代。
- librosa 0.11.0（Python 3.11、numpy 2.4）：讀成 22050 Hz；`beat_track` 取速度；`effects.hpss`（margin 2.0）分出和聲部分；`chroma_cqt` 算音高分佈。
- 主奏追蹤一：`pyin`（fmin 180 Hz、fmax 1400 Hz、frame 2048、hop 256），失敗（見 7.3）。
- 主奏追蹤二（和聲顯著度）：中間聲道（左右平均）的和聲部分做 CQT（從 E2 起、每八度 36 格、6 個八度、hop 256），把第 1～4 泛音以權重 1、0.6、0.4、0.3 疊加，在 G3～D6 之間取最大值，只留顯著度前 40% 的畫格。
- 立體聲：800 Hz～4 kHz 的 side（左減右）和 mid（左加右）平均能量比。
- 7.2 中 Fable 的重新量測（脈動、分組自相關、中間聲道主奏比例）和 Opus 的段落邊界統計，方法寫在 [搖滾獨奏_設計挑戰.md](搖滾獨奏_設計挑戰.md)；邊界統計可以用 `tests/samples.test.mjs` 的輸出重做。

## 8. 搖滾獨奏的慣例與玩法討論（2026-11-25）

- **搖滾 solo 通常用主音的小調五聲音階**，就算歌是大調也一樣，再加上藍調音（降五度）。挑戰後的修正：大調藍調（如 s21）時，小三度不能當停留的音，要自動推成大三度；一般大調歌用大調五聲音階。
- **快速樂句做不到一個動作一個音：**範例約每秒 6 個起音（大多是節奏組的八分音符）；鏡頭約每秒 30 張畫面、延遲約 60 ms。
- **「一個動作觸發一整段樂句」的問題：**起點、音、長度、結尾都由遊戲決定，玩家很快就沒有新鮮感；帥的感覺主要來自音色、延音、顫音和推弦。手的高度、上推、甩手、抖手在每秒 30 張畫面下其實是同一種訊號，很難分辨，也沒有「休息不觸發」的方法。
- 兩份挑戰文件的建議和待決事項見 [獨奏模式_設計挑戰.md](獨奏模式_設計挑戰.md)、[搖滾獨奏_設計挑戰.md](搖滾獨奏_設計挑戰.md)；**都還沒有決定。**

## 9. 開發環境上的坑（2026-11-25）

- **Windows 批次檔裡放中文會解析錯亂**（UTF-8 和 Big5 都試過，cmd 會把中文切斷當成指令）。做法：`開始玩.bat` 只有一行英文，呼叫 UTF-8（含 BOM）的 `tools/start.ps1`，中文訊息都在 PowerShell 顯示。
- **Python 的 `http.server` 在某些 Windows 上會把 `.js` 標成 `text/plain`**（讀登錄檔），瀏覽器就不載入 ES module。這是已知風險，開發用的電腦上沒有發生（實測回傳 `application/javascript`），屬於預防。`tools/start.ps1` 強制指定 `text/javascript` 和 `application/wasm`。
- 背景研究用的分析腳本放在暫存資料夾，沒有搬進專案；方法和數字記在第 7 節，真實歌曲的回歸測試改由 `tests/samples.test.mjs` 負責（WAV 用 `ffmpeg -i "samples/sample 14.mp3" -ac 2 -ar 44100 samples/s14.wav` 產生）。
